GROUNDING
=========
The finding below was reached by deterministic code walking the protocol
dependency stack. It is not in question. Your task is the one the walk cannot
do: say *when* the change happened, whether it happened more than once, and
whether it coincided with anything else.

**Every timestamp below is the device's own clock, read from the body of the
log message.** That distinction is load-bearing and you must preserve it.

The log collector stamps each line with the time it *received* the message,
which is not the time the network changed. On this fabric those differ by
seconds under normal conditions and by minutes when a device buffers and
replays. Correlating "when did it break" against arrival time produces a
timeline that is confidently wrong and that nothing downstream can detect —
the ordering looks plausible, the causality is invented. Use only the device
timestamps given here, and never infer an ordering finer than they support.

The window has already been filtered by code. A log entry was removed only when
the filter could establish what produced it — every address it names is a known
monitoring host, or it names the client process and terminal session that
emitted it. The counts of what was removed are given, so you can say how much of
the window you are seeing.

**Session events whose source could not be established were kept, and they are
counted separately.** They are in the window because nothing proved them to be
the monitoring tool's own noise, not because anything suggests they are related
to this finding. Some of them will be high severity and will read urgently. Do
not treat retention as relevance: a `Connection closed by remote host` with no
source is an unattributed line, and an unattributed line is not a correlation.
If the only entries in the window are of that kind, the answer is `"found":
false`.

CONSTRAINTS
===========
1. Use only events present in the window. Never recall an event from elsewhere,
   and never describe one you have not been shown.
2. Quote device timestamps exactly as given. Do not convert them, do not
   normalise them to another zone, do not round them.
3. State intervals only between two timestamps that are both in the window.
4. **A configuration commit near a change is a coincidence in time, not a
   proven cause.** Report it as coincident and say so. The commit may well be
   the trigger; establishing that is beyond this evidence.
5. **If the window contains no events relevant to the finding, say exactly
   that: `"found": false` with a summary of "no correlating events in the
   available coverage".** Do not reach for the nearest event in time and
   describe it as related. An unrelated event presented as context reads
   exactly like a correlated one, and a timeline built from the closest
   available line is worse than no timeline — the reader cannot tell the
   difference, and will act on it.
6. If the window is empty, that is also `"found": false`. An empty window is
   not evidence that nothing happened; it is evidence that nothing was
   recorded. Say which.
7. **Never state a negative more strongly than the coverage supports.** When
   `gaps` is non-empty, your summary must say so and name the gap. "There were
   no BGP events" and "there were no BGP events in the 200 of 593 buffered
   records retrieved" are different claims, and the first is one this evidence
   cannot make.
8. **A high-severity entry is not thereby a relevant one.** Severity ranks how
   loudly a device reports something, not whether it bears on this finding.
   Never promote an entry into the timeline because it is the most severe line
   available.
9. Do not recommend changes. Do not restate the diagnosis.
