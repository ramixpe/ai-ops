ios-xr-nettools · architecture

The trust boundary stack

Four invariants hold across every layer of this tool: platform resolves credential-free, the allowlist is checked before credentials load, no command is ever built by interpolation, and no unparsed device text ever reaches a model. Below is the actual chain a live MCP tool call passes through — from an untrusted caller to a lab device and back — with each enforcement point drawn where it really runs.

MCP REGISTRATION WRAPPER · RUNTIME

Two gates, every call

  • Inventory membership — any call carrying device_name is refused unless it names one of the 9 devices in inventory/lab.yaml, closing the gap where a direct MCP client (bypassing the event loop's pinned schema) could name any string as a device.
  • Evidence-backed object validity — for “asserted”-contract tools only (a BGP peer, an interface), mcp_epoch_validation.validate_asserted_object() checks the caller's identifier against evidence_cache.EvidenceCache, collected fresh from that device (10s TTL by default, 0 = always-live). A real address that simply isn't this device's own peer is refused the same way.

CI / TEST SUITE · MERGE-TIME

One gate, every merge

  • Manifest parity — the event loop's offline planning schema, the staged surface's live registered-tool schemas, and model_ingress.PIN_TABLE's declared parameters must agree exactly. A parameter added without a PIN_TABLE rule fails the build, not a live request.
