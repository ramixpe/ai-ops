# EER-013: a reproducibility floor for CI installs.
#
# This is a `pip install -c constraints.txt ...` constraints file, not a full
# lockfile: it pins exact versions for the packages CI actually installs
# (project runtime deps, the `dev`/`llm` extras, and the packaging/audit
# tools the CI-only build-artifact job installs directly) so a CI run today
# resolves the same graph as a CI run next month, instead of picking up
# whatever each package's maintainers happened to publish between the two.
# It does not add new dependencies on its own -- `pip install -c
# constraints.txt` only *constrains* packages that would be installed
# anyway; a name listed here that a given job never installs (e.g.
# pip-audit's own dependency tree, irrelevant to the plain `pip install -e
# ".[dev,llm]"` in the `test` job) is simply ignored for that job.
#
# Generated 2026-08-20 by `pip freeze` from a throwaway venv (never the
# shared `.venv` -- see CLAUDE.md's environment rules) with
# `pip install -e ".[dev,llm]"` plus `build`, `pytest-cov`, and `pip-audit`
# installed, on Python 3.11.14. Every version below is one actually
# resolved, installed, and exercised (full test suite green, wheel built,
# offline demo run from the built wheel, coverage measured, pip-audit run)
# during that verification -- not a guess. All satisfy the ranges declared
# in pyproject.toml as of the same commit.
#
# To refresh: create a throwaway venv, `pip install -e ".[dev,llm]" build
# pytest-cov pip-audit`, verify the suite and the offline demo, then
# `pip freeze` and re-pin. Review the diff -- a constraints bump is a
# reviewable, evidence-backed decision, same discipline as a pyproject.toml
# dependency bump (see EER-014's pip-audit step, which reports findings
# rather than silently bumping past them).
